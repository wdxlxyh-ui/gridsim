# 需求方案：数据持久化数据库设计

适用对象：GridSim 后端开发、前端开发、部署实施人员。

本方案解决的问题：当前测点实时值、趋势面板配置、运行统计只存在内存或浏览器 `localStorage` 中，进程重启或换浏览器后数据丢失，界面打开时拿到的是临时数据而非历史数据。

---

## 1. 结论摘要

| 决策项 | 结论 |
|--------|------|
| 数据库 | SQLite，驱动用纯 Go 实现 `modernc.org/sqlite` v1.56.0 |
| 部署形态 | 单文件嵌入式，随发行包落地，无需额外安装服务 |
| 分表策略 | 元数据共享单表 + 时序数据按实例独立表 `ts_<instance_id>` |
| 跨表查询 | 自动维护的 `UNION ALL` 视图 `v_samples`，可直接跨实例聚合 |
| **保留策略** | **时序数据固定 1 小时滚动窗口，超期立即丢弃，体积稳定在 20~40 MB** |
| 兼容性 | 三平台 `CGO_ENABLED=0` 交叉编译已实测通过，与现有 `build.sh` 约束一致 |
| 降级能力 | `--db=off` 可完全关闭，行为回退到当前版本 |

### 定位说明

本数据库是**滚动数据缓冲**，不是长期历史归档。它解决的是「界面打开时有数据可看、进程重启后最近 1 小时不丢」，不承担长周期趋势分析职责。需要长期留存的数据通过 CSV 导出到外部。

这个定位直接带来两个好处：体积上限可预测（不会撑满磁盘），以及无需复杂的分区与归档机制。

### 选型已通过实测验证

在编译服务器（go1.25.5 linux/amd64）实际验证，非理论推断：

```

  OK   linux/arm64    ->  8.9M
  OK   windows/amd64  ->  9.4M

journal_mode = wal
cross-table row: src=a ts=1 ioa=16385 v=1.5
cross-table row: src=b ts=1 ioa=16386 v=9.0
cross-table row: src=a ts=2 ioa=16385 v=2.5

batch insert: 50000 rows in 651ms  => 76833 rows/s
range query:  count=1000 avg=12487.5 in 652µs
```

结论要点：
- 纯 Go 驱动在 `CGO_ENABLED=0` 下三平台编译通过，不破坏现有交叉编译流程
- WAL 模式生效，支持读写并发（轮询读不阻塞采样写）
- 单事务批量写入约 7.7 万行/秒，远高于本项目采样量级
- 跨表与跨库（`ATTACH`）查询均可用
- 代价：二进制体积净增约 7.5 MB，`gridsim` 由 11 MB 增至约 18.5 MB

## 2. 选型分析

### 2.1 硬性约束

`build.sh` 第 143 行对三平台统一使用 `CGO_ENABLED=0`：

```bash
GOOS="$goos" GOARCH="$goarch" CGO_ENABLED=0 \
```

这条约束直接决定选型边界：任何依赖 CGO 的驱动都会导致交叉编译失败或需要引入交叉编译工具链，破坏现有一键构建流程。

### 2.2 候选对比

| 方案 | SQL 支持 | 跨表查询 | CGO | 部署复杂度 | 结论 |
|------|---------|---------|-----|-----------|------|
| `modernc.org/sqlite` | 完整 SQL | 支持 | 不需要 | 单文件，零运维 | **采用** |
| `mattn/go-sqlite3` | 完整 SQL | 支持 | 需要 | 单文件 | 排除：破坏 `CGO_ENABLED=0` |
| PostgreSQL / MySQL | 完整 SQL | 支持 | 不需要 | 需独立部署与运维 | 排除：模拟器定位为便携测试工具 |
| DuckDB | 分析型 SQL | 支持 | 需要 | 单文件 | 排除：需 CGO，且写入场景不占优 |
| bbolt / BadgerDB | 无 SQL | 需手写 | 不需要 | 单文件 | 排除：无法满足跨表查询与聚合 |
| InfluxDB / TDengine | 类 SQL | 支持 | 不需要 | 需独立部署 | 排除：运维成本不匹配 |
| 保持 JSON 文件 | 无 | 无 | 不需要 | 最简 | 排除：无法支撑时序查询与聚合 |

选择 SQLite 的核心理由是兼容性：单文件随发行包分发，Windows 与 Linux 行为一致，用户无需安装任何服务，与现有「解压即用」的交付方式一致。

### 2.3 关于「多实例不同表」的取舍说明

需求提出「多实例不同的表，但也可以跨表查询」。这两个目标存在张力，需要明确取舍：

- 纯物理分表：写入隔离好、单实例清理只需 `DROP TABLE`，但跨表查询必须动态拼接 `UNION ALL`，SQL 复杂度随实例数增长
- 纯单表加 `instance_id` 字段：查询最简单，但单表行数随实例累加，清理单个实例需要大范围 `DELETE`

本方案采用折中：**时序数据物理分表，跨表查询由系统自动维护的视图承担**。这样既满足按实例隔离，又让上层查询无需感知分表细节。视图在实例增删时自动重建，对调用方透明。

## 3. 数据库结构设计

### 3.1 文件布局

```
config/
└── db/
    ├── gridsim.db          # 主库（元数据 + 时序表 + 视图）
    ├── gridsim.db-wal      # WAL 日志（运行时）
    └── gridsim.db-shm      # 共享内存索引（运行时）
```

放在 `config/db/` 之下，可复用现有部署流程中「备份 config、恢复 config」的既有逻辑，无需改动 `gridsim-deploy` 工作流。

### 3.2 连接参数

```
file:config/db/gridsim.db
  ?_pragma=journal_mode(WAL)        # 读写并发，轮询读不阻塞采样写
  &_pragma=synchronous(NORMAL)      # 兼顾安全与吞吐
  &_pragma=busy_timeout(5000)       # 锁等待 5s，避免瞬时并发报错
  &_pragma=foreign_keys(ON)         # 启用外键约束
  &_pragma=auto_vacuum(NONE)        # 固定窗口滚动，空闲页由写入复用，不做自动回收
```

`auto_vacuum(NONE)` 必须在首次建库时确定，后续变更需要全量 `VACUUM`。选择理由见 3.9 节空间回收策略。

### 3.3 元数据层（共享单表）

```sql
-- Schema 版本管理，支撑后续平滑升级
CREATE TABLE IF NOT EXISTS schema_version (
    version     INTEGER PRIMARY KEY,
    applied_at  INTEGER NOT NULL,          -- Unix 毫秒
    description TEXT
);

-- 实例注册表，镜像 instances.json，DB 不作为配置权威源
CREATE TABLE IF NOT EXISTS instances (
    id           TEXT PRIMARY KEY,          -- 如 8e546cecbce3
    name         TEXT NOT NULL,
    protocol     TEXT NOT NULL,             -- iec104 / modbus_tcp / microgrid / iec104_client
    port         INTEGER,
    xlsx_file    TEXT,
    ts_table     TEXT NOT NULL,             -- 对应时序表名，如 ts_8e546cecbce3
    created_at   INTEGER NOT NULL,
    updated_at   INTEGER NOT NULL,
    deleted_at   INTEGER                    -- 软删除，保留历史数据可查
);

-- 测点定义，跨实例统一存储，便于按名称跨实例检索
CREATE TABLE IF NOT EXISTS points (
    instance_id  TEXT NOT NULL,
    ioa          INTEGER NOT NULL,
    name         TEXT NOT NULL,
    point_type   TEXT NOT NULL,             -- AI / DI / PI / AO / DO
    value_type   TEXT,                      -- FLOAT / DOUBLE / INT / BIT
    unit         TEXT,
    coefficient  REAL DEFAULT 1,
    base_value   REAL DEFAULT 0,
    func_code    INTEGER,                   -- Modbus 功能码
    reg_addr     INTEGER,                   -- Modbus 寄存器地址
    updated_at   INTEGER NOT NULL,
    PRIMARY KEY (instance_id, ioa),
    FOREIGN KEY (instance_id) REFERENCES instances(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_points_name ON points(name);
CREATE INDEX IF NOT EXISTS idx_points_type ON points(instance_id, point_type);
```

### 3.4 时序层（每实例独立表）

建表模板，`<ID>` 为实例 ID：

```sql
CREATE TABLE IF NOT EXISTS ts_<ID> (
    ioa        INTEGER NOT NULL,
    ts         INTEGER NOT NULL,            -- Unix 毫秒
    value      REAL,                        -- AI/AO 数值
    bool_value INTEGER,                     -- DI/DO 布尔，0/1
    int_value  INTEGER,                     -- PI 累计量
    qds        INTEGER DEFAULT 0,           -- 品质描述位掩码
    PRIMARY KEY (ioa, ts)
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS idx_ts_<ID>_ts ON ts_<ID>(ts);
```

设计说明：

- 主键为 `(ioa, ts)` 且使用 `WITHOUT ROWID`，按测点聚簇存储，趋势查询「某测点某时间段」为顺序扫描，实测 1000 行聚合 652µs
- 额外建 `ts` 单列索引，支撑「某时刻全实例快照」类查询
- `qds` 用位掩码存储五种品质位（无效/非当前/替代/溢出/闭锁），与现有 `QualityDescriptor` 结构一一对应

**品质位掩码定义**（与 `model.QualityDescriptor` 对齐）：

| 位 | 含义 | 值 |
|---|------|---|
| bit0 | Invalid（无效） | 1 |
| bit1 | NotTopical（非当前） | 2 |
| bit2 | Substituted（替代） | 4 |
| bit3 | Overflow（溢出） | 8 |
| bit4 | Blocked（闭锁） | 16 |

### 3.5 跨表查询视图

实例增删时自动重建，调用方只查视图，无需感知分表：

```sql
DROP VIEW IF EXISTS v_samples;
CREATE VIEW v_samples AS
    SELECT '8e546cecbce3' AS instance_id, ioa, ts, value, bool_value, int_value, qds FROM ts_8e546cecbce3
    UNION ALL
    SELECT '05438bf8b615' AS instance_id, ioa, ts, value, bool_value, int_value, qds FROM ts_05438bf8b615
    UNION ALL
    SELECT 'f2f210dd7027' AS instance_id, ioa, ts, value, bool_value, int_value, qds FROM ts_f2f210dd7027;
```

配套的语义化视图，把测点名称一并带出：

```sql
DROP VIEW IF EXISTS v_samples_named;
CREATE VIEW v_samples_named AS
SELECT s.instance_id, i.name AS instance_name, s.ioa, p.name AS point_name,
       p.point_type, p.unit, s.ts, s.value, s.bool_value, s.int_value, s.qds
FROM v_samples s
LEFT JOIN points    p ON p.instance_id = s.instance_id AND p.ioa = s.ioa
LEFT JOIN instances i ON i.id = s.instance_id;
```

跨实例查询示例：

```sql
-- 跨实例对比同名测点最近 15 分钟趋势
SELECT instance_name, point_name, ts, value
FROM v_samples_named
WHERE point_name = 'P_Total'
  AND ts >= (strftime('%s','now') - 900) * 1000
ORDER BY ts;

-- 跨实例统计各实例样本量与时间跨度
SELECT instance_id, COUNT(*) AS samples,
       MIN(ts) AS first_ts, MAX(ts) AS last_ts
FROM v_samples
GROUP BY instance_id;
```

如实例数量增长到视图 `UNION ALL` 分支过多（经验阈值 200 个以上），改用按需拼接查询：仅对本次查询涉及的实例生成 `UNION ALL`，避免全量视图开销。

### 3.6 策略持久化层

替代当前 `config/auto_changes/{instance_id}.json`，并解决前一份方案中提出的策略重启丢失问题：

```sql
CREATE TABLE IF NOT EXISTS auto_change_configs (
    instance_id TEXT NOT NULL,
    ioa         INTEGER NOT NULL,
    strategy    TEXT NOT NULL,              -- increment / random / csv / soc / custom ...
    enabled     INTEGER NOT NULL DEFAULT 1,
    params_json TEXT NOT NULL,              -- StrategyParams 序列化，保留字段扩展弹性
    updated_at  INTEGER NOT NULL,
    PRIMARY KEY (instance_id, ioa),
    FOREIGN KEY (instance_id) REFERENCES instances(id) ON DELETE CASCADE
);
```

`params_json` 保留 JSON 存储而非拆列，原因是 `StrategyParams` 有 30 余个可选字段且随策略类型扩展，拆列会导致大量空列与频繁 schema 变更。

### 3.9 数据保留策略：1 小时滚动窗口

时序数据采用**固定 1 小时滚动窗口**：新数据持续写入，超过 1 小时的数据立即丢弃。数据库体积随之稳定在一个可预测的水位，不随运行时长增长。

#### 稳态体积估算

按每行约 45 字节（含主键聚簇与 `ts` 索引开销）估算：

| 规模 | 行数（1 小时窗口） | 稳态体积（约） |
|------|------------------|--------------|
| 6 实例 × 30 点 × 1 Hz | 64.8 万 | 30 MB |
| 6 实例 × 30 点 × 1 Hz + 仅记录变化（10%） | 6.5 万 | 3 MB |
| 20 实例 × 100 点 × 1 Hz | 720 万 | 320 MB |
| 20 实例 × 100 点 × 5s 采样 | 144 万 | 65 MB |

当前环境为 6 实例，稳态体积约 30 MB，属于完全可接受范围。因此**死区过滤（仅记录变化）从必需项降级为可选优化**，默认关闭以保证数据完整性；仅在实例数或测点数大幅增长时再启用。

`max_db_size_mb` 保护仍然保留，作为极端规模下的兜底：超过阈值时自动收窄保留窗口并告警。

#### 配置项

```sql
CREATE TABLE IF NOT EXISTS retention_config (
    key         TEXT PRIMARY KEY,
    value       TEXT NOT NULL,
    updated_at  INTEGER NOT NULL
);
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `retention_minutes` | `60` | 时序数据保留分钟数，固定 1 小时窗口 |
| `cleanup_interval_s` | `60` | 清理执行间隔，每分钟一次 |
| `sample_interval_ms` | `1000` | 落库采样周期，与 UI 轮询解耦 |
| `deadband_enabled` | `false` | 是否仅记录变化值，默认关闭 |
| `deadband_abs` | `0` | 绝对死区阈值 |
| `max_db_size_mb` | `1024` | 体积上限，超限自动收窄窗口并告警 |
| `event_retention_days` | `7` | 事件与审计类数据保留天数，见分层说明 |

`retention_minutes` 允许调整，但界面上限制为不超过 240（4 小时），避免误配导致体积失控。

#### 分层保留

时序采样与事件审计的数据特征完全不同，采用不同保留期：

| 数据类别 | 表 | 频率 | 保留期 | 理由 |
|---------|---|------|--------|------|
| 时序采样 | `ts_<ID>` | 高频（1 Hz） | **1 小时** | 体积主要来源，滚动丢弃 |
| 实例事件 | `instance_events` | 低频（启停、连接） | 7 天 | 日均数十行，体积可忽略，保留有排查价值 |
| 控制审计 | `control_logs` | 低频（遥控遥调） | 7 天 | 审计追溯需要，日均数百行 |
| 统计快照 | `instance_stats` | 每分钟 1 行/实例 | 7 天 | 6 实例约 6 万行/周，约 3 MB |
| 元数据与配置 | `instances`、`points`、`auto_change_configs`、趋势配置 | 变更时写入 | **永久** | 配置数据必须持久 |

事件类数据 7 天保留总计增加约 5 MB，换取遥控指令与实例启停的可追溯性，性价比高。若需进一步压缩空间，可将 `event_retention_days` 调低。

#### 清理执行

清理与刷盘由**同一个写入 goroutine 串行执行**，这是关键实现约束：WAL 模式下写操作互斥，若清理与写入并发会产生锁竞争与 `SQLITE_BUSY`。

```go
// 写入循环中，每 cleanup_interval_s 触发一次清理
func (w *Writer) loop() {
    flushTick := time.NewTicker(time.Duration(w.flushMs) * time.Millisecond)
    cleanTick := time.NewTicker(time.Duration(w.cleanupSec) * time.Second)
    defer flushTick.Stop()
    defer cleanTick.Stop()

    for {
        select {
        case s := <-w.ch:
            w.batch = append(w.batch, s)
            if len(w.batch) >= w.maxBatch {
                w.flush()
            }
        case <-flushTick.C:
            w.flush()
        case <-cleanTick.C:
            w.flush()      // 先刷盘，保证清理不误删刚入队数据
            w.cleanup()    // 与写入同一 goroutine，无锁竞争
        case <-w.done:
            w.flush()
            return
        }
    }
}
```

清理语句按实例逐表执行，单事务提交：

```sql
DELETE FROM ts_<ID> WHERE ts < :cutoff_ms;   -- cutoff = now - retention_minutes * 60000
```

由于主键为 `(ioa, ts)` 且 `ts` 有独立索引，按时间删除可走索引定位，不会全表扫描。

#### 空间回收策略

固定窗口滚动场景下，**不执行 `VACUUM` 或 `incremental_vacuum`**，这是有意的设计选择：

- 删除产生的空闲页会被后续写入自动复用，文件大小自然稳定在峰值水位
- 频繁 `VACUUM` 会带来大量额外 I/O 与长时间写锁，反而影响采样写入
- 稳态下文件大小基本不变，无需回收

建库时设置 `auto_vacuum = NONE`（SQLite 默认值），并保留手工回收入口 `POST /api/v1/db/vacuum` 供特殊场景使用（例如大幅调低保留窗口后希望立即释放磁盘）。

需要注意：`auto_vacuum` 只能在建库时或全量 `VACUUM` 时变更，因此该决策必须在首次建库时确定。

WAL 文件另需控制：删除操作会产生大量 WAL 页，每次清理后执行一次被动检查点，避免 WAL 无界增长。

```sql
PRAGMA wal_checkpoint(PASSIVE);
```

服务退出时执行 `PRAGMA wal_checkpoint(TRUNCATE)` 将 WAL 归零。

## 4. 后端设计

### 4.1 模块划分

```
internal/store/                     新增
```

### 4.2 写入管道

直接在采样回调里同步写库会把数据库延迟引入协议栈，必须解耦：

```go
// internal/store/writer.go 设计要点
type Sample struct {
    InstanceID string
    IOA        uint32
    TS         int64
    Value      float64
    BoolValue  bool
    IntValue   int32
    QDS        uint8
}

type Writer struct {
    ch         chan Sample        // 有缓冲通道，容量 8192
    batch      []Sample           // 批量缓冲
    flushMs    int                // 刷盘间隔，默认 1000ms
    maxBatch   int                // 批量上限，默认 2000 条
    cleanupSec int                // 清理间隔，默认 60s
    retainMin  int                // 保留窗口，默认 60 分钟
    deadband   bool               // 死区过滤，默认关闭
    lastVal    map[string]Sample  // 死区比较基准，key = instanceID:ioa
    dropped    atomic.Int64       // 丢弃计数，暴露到 db/status
}
```

行为约定：

1. `Push` 为非阻塞，通道满时丢弃最旧样本并累加丢弃计数，**保证协议栈永不因数据库阻塞**
2. 死区过滤（若启用）在入队前完成，减少通道压力；默认关闭，保证 1 小时窗口内数据完整
3. 刷盘由「满 `maxBatch` 条」或「到 `flushMs` 间隔」触发，取先到者
4. 每批一个事务，按实例分组后走各自的预编译语句，实测 7.7 万行/秒余量充足
5. **滚动窗口清理由同一 goroutine 串行执行**，避免与写入争抢 WAL 写锁（详见 3.9）
6. 写入失败记录日志并计数，不向上传播错误，不影响仿真运行

### 4.3 表名安全

实例 ID 会拼进表名，必须防注入。ID 由 `generateID()` 生成为十六进制字符串，但仍需强校验：

```go
var reInstanceID = regexp.MustCompile(`^[0-9a-f]{6,32}$`)

func tsTableName(instanceID string) (string, error) {
    if !reInstanceID.MatchString(instanceID) {
        return "", fmt.Errorf("invalid instance id: %q", instanceID)
    }
    return "ts_" + instanceID, nil
}
```

所有涉及表名拼接的位置统一走该函数，值参数一律使用占位符绑定，不做字符串拼接。

### 4.4 生命周期挂载点

| 时机 | 动作 |
|------|------|
| 服务启动 | 打开数据库、执行迁移、重建 `v_samples`、启动清理任务 |
| 创建实例 | `instances` 插入记录、建 `ts_<ID>` 表、重建视图 |
| 启动实例 | 同步 `points` 定义、**从 `auto_change_configs` 恢复策略**、记录 start 事件 |
| 运行采样 | 经 `Writer` 异步批量落库 |
| 遥控遥调 | 写 `control_logs` |
| 停止实例 | 记录 stop 事件、刷盘 `Writer` 缓冲 |
| 删除实例 | 软删除 `instances.deleted_at`；按用户选择决定是否 `DROP TABLE ts_<ID>` |
| 服务退出 | 刷盘、`PRAGMA wal_checkpoint(TRUNCATE)`、关闭连接 |

其中「启动实例时恢复策略」直接修复了上一份方案中标记为 P1 的缺陷：实例重启后策略不再丢失。

### 4.6 配置与启动参数


`auto` 是保证兼容性的关键：只读文件系统、磁盘满、权限不足等场景下自动降级为当前行为，服务照常启动，仅记录告警日志。

`--db-retention-minutes` 上限限制为 240。超过该值时启动阶段直接拒绝并提示，避免误配导致体积失控。

```typescript
const MAX_BACKFILL_MIN = 60      // 与后端滚动窗口对齐

async function backfillHistory() {
  if (panelTraces.value.length === 0) return
  const span = Math.min(props.timeRange, MAX_BACKFILL_MIN)
  const to = Date.now()
      , from = to - span * 60 * 1000
  const byInst = groupByInstance(panelTraces.value)

  for (const [instId, ioas] of byInst) {
    try {
      const res = await getHistory(instId, ioas, from, to)
      for (const s of res.series) {
        const tr = panelTraces.value.find(t => t.instId === instId && t.ioa === s.ioa)
        if (tr) tr.data = s.samples          // 直接用 [ts, value] 数组

      if (res.truncated) ElMessage.warning('历史数据过多已截断，建议缩小时间范围')
    } catch {
      // 数据库未启用时静默跳过，退化为仅实时累积
    }
  }
  updateChart()
}
```

### 5.4 配置迁移与降级

`localStorage` 迁移采用一次性、幂等、用户可见的方式：

```typescript
// 首次加载时检测本地遗留配置并提示迁移
async function migrateLocalConfigIfNeeded() {
  const done = localStorage.getItem('trend_migrated_v1')
  if (done) return

  const panels = localStorage.getItem('trend_panels')
  const templates = localStorage.getItem('trend_templates')
  if (!panels && !templates) {
    localStorage.setItem('trend_migrated_v1', '1')
    return
  }

  try {
    await ElMessageBox.confirm(
      '检测到浏览器本地保存的趋势配置，是否上传到服务端以便跨浏览器使用？',
      '配置迁移',
      { confirmButtonText: '上传', cancelButtonText: '暂不处理', type: 'info' }
    )
    await importLocalTrendConfig({
      panels: JSON.parse(panels || '[]'),
      templates: JSON.parse(templates || '[]'),
    })
    localStorage.setItem('trend_migrated_v1', '1')
    ElMessage.success('配置已上传到服务端')
  } catch {
    // 用户取消：不重复打扰，但保留本地数据不删除

  }

```

迁移原则：

- 不删除本地数据，迁移失败可重试，避免配置丢失
- 服务端不可用时，前端继续使用 `localStorage`，功能不中断
- 通过 `GET /api/v1/db/status` 探测能力，动态显隐历史查询相关入口

## 6. 兼容性保证

这是本方案的重点约束，按四个维度分别保证。

### 6.1 平台与构建兼容

| 项目 | 保证方式 | 验证状态 |
|------|---------|---------|
| 三平台交叉编译 | 选用纯 Go 驱动，不引入 CGO | ✅ 已实测三平台通过 |
| `build.sh` 流程 | 不修改 `CGO_ENABLED=0` 与任何构建参数 | ✅ 无需改动 |
| Windows 一致性 | SQLite 单文件，路径由 Go 标准库处理 | 待部署验证 |
| ARM64 设备 | `linux/arm64` 编译产物已生成 | ✅ 已实测通过 |
| 体积影响 | 净增约 7.5 MB，发行包由 9.1 MB 增至约 12~13 MB | ✅ 已实测 |

### 6.2 向后兼容

| 风险点 | 保证措施 |
|--------|---------|
| 现有 API 被破坏 | 全部能力走新增路径，既有接口的请求与响应结构零改动 |
| 旧配置无法加载 | `instances.json` 与点表 `.xlsx` 仍为配置权威源，数据库只做镜像与数据层 |
| 旧发行包回退 | 数据库文件独立存放于 `config/db/`，回退旧版本时旧程序忽略该目录即可 |
| 数据库文件损坏 | 启动时做完整性检查，失败则重命名为 `.corrupt-<时间戳>` 并新建，服务不阻塞 |
| 磁盘满或只读 | `--db=auto` 自动降级，记录告警，仿真功能不受影响 |
| 前端新旧混搭 | 前端通过 `db/status` 探测能力，旧后端下自动隐藏新功能 |

关键设计取舍：**数据库不作为配置权威源**。`instances.json`、`auto_changes/*.json`、点表文件继续保留并正常写入，数据库中的对应表是镜像。这样即使数据库被删除或损坏，实例配置与策略配置都不会丢失，只丢失历史时序数据。代价是配置需要双写，收益是回退路径始终可用。

### 6.3 Schema 演进兼容

```go
// internal/store/migrate.go
var migrations = []Migration{
    {Version: 1, Desc: "初始 schema：元数据、时序、策略、趋势配置", Up: migrateV1},
    {Version: 2, Desc: "新增事件与控制审计表", Up: migrateV2},
    // 后续版本只追加，不修改历史迁移
}
```

约定：

- 迁移只追加，已发布的迁移函数不得修改
- 每个迁移在单个事务内完成，失败则整体回滚
- 新增列一律带默认值，保证旧数据可读
- 不做破坏性变更（不删列、不改列类型）；确需重构时新建表并保留旧表一个大版本周期
- 高版本数据库遇到低版本程序时，程序检测到 `schema_version` 超出自身支持范围，降级为只读或关闭数据库，不做写入

### 6.4 部署流程兼容

现有 `gridsim-deploy` 工作流已包含「备份 config → 解压新包 → 恢复 config」。数据库放在 `config/db/` 之下即自动被这套逻辑覆盖，无需修改部署 skill。

1 小时滚动窗口把体积压到约 30 MB，使备份成本从「数百 MB、明显变慢」降为「秒级完成」，原先的备份性能顾虑基本消除。但仍有两点需注意：

1. **停服顺序**：必须先 `systemctl stop gridsim` 再操作数据库文件，避免 WAL 状态不一致。现有流程已满足该顺序
2. **备份内容混杂**：数据库同时包含临时时序数据（无备份价值，恢复后 1 分钟内即被清理）与配置数据（趋势模板、策略镜像，有备份价值）。默认整体备份最简单，30 MB 量级完全可接受

若后续实例规模显著增长导致体积超过百 MB，再考虑拆分为两个文件：

| 文件 | 内容 | 备份策略 |
|------|------|---------|
| `gridsim.db` | 元数据、策略、趋势配置、事件审计 | 需要备份 |
| `gridsim-ts.db` | 时序采样数据 | 不备份，`ATTACH` 挂载使用 |

跨库查询能力已在 PoC 中验证（`ATTACH cross-DB` 通过），因此拆分不影响跨表查询设计。本阶段不拆分，保持单文件以降低复杂度。

部署脚本可选优化（本方案不改动 skill，仅提出建议）：

```bash
# 停服后先做检查点，保证备份文件自洽
sqlite3 /home/envuser/IEC/gridsim/config/db/gridsim.db "PRAGMA wal_checkpoint(TRUNCATE);" 2>/dev/null || true
# 正常备份 config（含数据库，约 30 MB，秒级完成）
cp -r /home/envuser/IEC/gridsim/config/* "$BACKUP/"
```

注意：编译服务器上未必安装 `sqlite3` 命令行工具。若不可用可跳过该步，程序退出时已执行 `TRUNCATE` 检查点，备份文件仍然自洽。

|------|------|------|
| 时序数据膨胀撑满磁盘 | 服务不可用 | 1 小时滚动窗口使体积稳定在约 30 MB；`max_db_size_mb` 兜底，超限自动收窄窗口并告警 |
| 高频删除导致 WAL 无界增长 | 磁盘占用异常 | 每次清理后执行 `wal_checkpoint(PASSIVE)`，退出时 `TRUNCATE` |
| 清理与写入争抢写锁 | 出现 `SQLITE_BUSY`、采样丢点 | 清理与刷盘在同一 goroutine 串行执行；`busy_timeout=5000` 兜底 |
| 页碎片累积 | 文件虚增 | `auto_vacuum=NONE`，空闲页由后续写入复用，稳态文件大小不增长 |
| 数据库写入阻塞协议栈 | 仿真时序失真 | 写入全异步，通道满即丢弃并计数，协议栈永不等待数据库 |
| 用户误期望长期历史 | 使用困惑、数据「丢失」投诉 | 界面明示 1 小时窗口边界；引导用 CSV 导出做长期留存 |
| 二进制体积增加 7.5 MB | 分发成本上升 | 已实测确认可接受；如需控制，可将数据库能力编译为可选 build tag |
| 表名注入 | 数据库被破坏 | 实例 ID 强正则校验 + 统一表名构造函数 + 值参数全部占位符绑定 |
| 高并发实例数下视图膨胀 | 查询变慢 | 超过 200 实例改为按需拼接查询，不用全量视图 |
| 配置双写不一致 | 界面与实际行为不符 | 明确 JSON 为权威源，数据库为镜像；启动时以 JSON 为准回填数据库 |
